# Экономия: где в проекте деньги и как их не тратить

Принцип: если есть вариант дешевле без потери качества — берём дешевле.

## Где деньги вообще есть

| Статья | Стоимость | Решение |
| --- | --- | --- |
| Разбор резюме | **0** | Claude Code CLI по подписке (фаза 2.5) |
| Сопроводительные письма | **0** | то же |
| Генерация skills.yaml, фикстур, eval-набора | **0** | то же, задача TOOLING |
| Разбор Telegram-постов | **0** | Ollama локально |
| Эмбеддинги | **0** | bge-m3 локально |
| JSearch | **0** | бесплатный тариф, 100 запросов в сутки |
| Postgres | **0** | Docker локально |
| **Re-rank вакансий** | **единственная реальная трата** | см. ниже |
| Хостинг | опционально | см. раздел про деплой |

Наивный расход re-rank: 30 вакансий × ~3k входных токенов × 4 прогона в
сутки ≈ 360k токенов/день. На Sonnet это порядка $20 в месяц.

Четыре меры ниже срезают это примерно в двадцать раз.

---

## 1. Не пересчитывать неизменившееся — дельта к фазе 5

**Экономия: ~10×. Самая большая мера, и это не оптимизация, а
исправление логики.**

Скор не меняется, если не изменились ни вакансия, ни профиль, ни веса.
После первого прогона новых вакансий в сутки будет 20–50, а не 120.

```
Re-rank вызывается ТОЛЬКО для вакансий, у которых выполнено одно из:
  - нет записи в match для текущего profile_id
  - vacancy.embedding_text_hash изменился с момента scored_at
  - профиль изменился (profile.updated_at > match.scored_at)
  - изменилась версия конфига весов (добавить
    match.scoring_config_version SMALLINT)

Механика хеша уже есть с фазы 3 — применить её и к скорингу.

Rule-скор пересчитывать можно свободно, он бесплатный. Дорогой только
LLM-этап.

Метрика в отчёте прогона: сколько вакансий пропущено как
неизменившиеся. Если после второго прогона это число близко к нулю —
инвалидация сломана, и это надо увидеть сразу.
```

## 2. Message Batches API — минус 50% — дельта к фазам 5 и 9

**Экономия: ровно половина от остатка, без единого компромисса.**

У Anthropic есть Batches API со скидкой 50% для асинхронной обработки.
Результат в пределах суток, обычно значительно быстрее.

Re-rank — фоновая джоба по расписанию. Латентность там не имеет
значения. Значит половина цены сейчас отдаётся ни за что.

```
В AnthropicAPIProvider добавить режим batch:
  - complete_json_batch(items) — собирает батч, отправляет,
    опрашивает статус, разбирает результаты
  - используется планировщиком для RERANK
  - синхронный путь остаётся для VACANCY_PARSE (человек ждёт ответа
    при ручном импорте)
  - LLMUsage помечает batch=true, стоимость считается со скидкой
  - таймаут ожидания и корректная обработка частично провалившихся
    батчей: неудавшиеся элементы падают на rule-only, не роняют прогон

Проверить перед реализацией: работает ли кэширование промта вместе с
батчами. Если да — экономии складываются.
```

## 3. Две ступени: дешёвая модель просеивает — дельта к фазе 5

**Экономия: ~60% от остатка.**

Заложено в фазе 2.5 как `RERANK_STAGE_MODELS`, пора включить.

```
Ступень 1: дешёвая модель (Haiku) проходит все N кандидатов с
rule_score >= порога. Задача простая: грубая релевантность, отсев
явно чужого. Короткий выход: score, 3–5 недостающих скиллов, одна
строка вердикта.

Ступень 2: Sonnet обрабатывает только топ-10 после первой ступени.
Полный разбор: matched/missing, red_flags, вердикт, application_angle.

Вакансии, не прошедшие первую ступень, получают итоговый скор от неё
и confidence=low. Они не выбрасываются, просто не разбираются
подробно.

Модели ступеней и размеры выборок — в конфиге.
```

## 4. Кэширование промта — уже заложено, проверить применение

Профиль кандидата и deal-breakers одинаковы во всех вызовах прогона.
`cache_control` на **первом** блоке, вакансия после него. Заложено в
фазе 2.5; в фазе 5 проверить, что реально применяется — тестом на
собранный запрос, а не на результат.

## 5. Потолок, который прерывает

Самая дорогая ошибка — не цена за токен, а баг, из-за которого прогон
начинает пересчитывать всё подряд. `LLM_MAX_COST_PER_RUN_USD` лежит в
`.env` с фазы 0 и, скорее всего, ничего не делает.

```
Сделать потолок ДЕЙСТВУЮЩИМ:
  - счётчик стоимости прогона проверяется перед каждым вызовом
  - превышение → прогон прерывается с ERROR и записью в
    PipelineRun.errors, а не продолжается с предупреждением
  - отдельный дневной потолок LLM_MAX_COST_PER_DAY_USD, счётчик в БД
    (таблица source_quota из фазы 3 подходит по форме — обобщить
    её до quota(scope, day, used))
  - тест: искусственно завышенная стоимость обрывает прогон
```

## 6. Деплой: возможно, сервер не нужен — дельта к фазе 11

Фаза 11 предполагала VPS. Но пользователь у системы один.

**Вариант А, бесплатный.** Планировщик на ноутбуке через Task
Scheduler: прогон при включении машины и раз в N часов, пока работает.
Для поиска работы «два прогона в те дни, когда ноутбук включён» —
достаточно. Дашборд поднимается локально по требованию.
Минус: пропуски в дни, когда машина выключена. Для job-alerts из почты
это не страшно — письма никуда не денутся, IMAP их отдаст позже.

**Вариант Б, тоже бесплатный.** Использовать уже оплаченную ёмкость:
у пользователя есть Amvera (EuroRazbor) и Beget (парсер панорам).
Проверить, есть ли там место под ещё один контейнер и Postgres.

**Вариант В, платный.** Отдельный VPS — только если А и Б не подходят.
Требования скромные: 2 ГБ RAM хватит без модели эмбеддингов на борту
(её можно считать локально и класть векторы в БД), 4 ГБ — с моделью.

Решение принимать в фазе 11, но фазу 9 (планировщик) писать так, чтобы
работали все три варианта: никаких предположений о непрерывной работе
процесса, состояние только в БД, пропущенный прогон навёрстывается.

## Порядок внедрения

1. **Фаза 5** — пункты 1, 3, 4, 5. Инвалидация и потолок обязательны
   до первого реального прогона скоринга, иначе первая же ошибка
   обойдётся дороже всей экономии.
2. **Фаза 9** — пункт 2, батчи вместе с планировщиком.
3. **Фаза 11** — пункт 6.

## Что измерять

В отчёт каждого прогона:

```
вакансий рассмотрено       N
пропущено как неизменившиеся  M   <- если ~0 на втором прогоне, инвалидация сломана
ступень 1 (дешёвая)        K вызовов, $X
ступень 2 (дорогая)        L вызовов, $Y
кэш промта                 попаданий Z
батч                       да/нет, скидка учтена
итого за прогон            $
итого за сутки             $ / потолок
```

Без этих цифр экономия — предположение. С ними видно, что реально
работает.
