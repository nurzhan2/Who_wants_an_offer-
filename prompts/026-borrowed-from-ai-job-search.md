# Заимствования из `MadsLorentzen/ai-job-search`

Разбор чужого проекта, решающего соседнюю задачу. Он про «откликнуться»,
мы про «найти и отранжировать». Архитектуры несовместимы (у него файлы и
Claude Code без БД), поэтому берём идеи, а не код.

Ниже — только то, что реально внедряем, разложенное по фазам.

## 1. ATS-проверка резюме → новая фаза 2.6, делать сразу

**Самое ценное. Машинерия уже написана в фазе 2, осталось развернуть наружу.**

Их `/apply` извлекает текстовый слой скомпилированного PDF и проверяет,
что видит ATS-парсер. Наш вывод из фазы 2:

```
ЗАРПЛАТА покрытие тестами с 30 до 78 процентов.
от 1 800 000 KZT Стек: Python 3, FastAPI, PostgreSQL, Redis, Kafka, Docker
НАВЫКИ Студия «Пиксель-Мираж» (фриланс, part-time) — удалённо
```

Это не дефект pdfplumber — это то, что видит ATS на hh, Greenhouse,
Workable, Lever. Мы обошли проблему для себя, отправив PDF в LLM
напрямую; работодатель так не умеет.

### Промт

```
Фаза 2.6. Прочитай CLAUDE.md, app/resume/extractor.py и результат разбора
двухколоночного PDF из фазы 2.

ЗАДАЧА: проверка резюме на машиночитаемость для ATS. Новый код
минимальный — сравниваем то, что уже умеем извлекать двумя способами.

1. app/resume/ats_check.py — AtsReport:
   - contact_extractable: почта, телефон, ссылки присутствуют в текстовом
     слое как ЛИТЕРАЛЬНЫЙ текст, а не как иконка или картинка. Регексы
     по извлечённому тексту, а не по структуре от LLM
   - reading_order_ok: детект интерливинга колонок. Метод: берём
     структуру, извлечённую LLM (эталон — там вёрстка прочитана верно),
     и текстовый слой pdfplumber; ищем в тексте фрагменты, где название
     компании и не связанная с ней строка склеены. Практический признак:
     заголовок секции (НАВЫКИ, ОПЫТ, ЗАРПЛАТА) внутри строки, а не в её
     начале
   - dates_extractable: периоды работы находятся в текстовом слое
   - sections_detected: какие стандартные секции ATS увидит
   - glyph_damage: доля непечатаемых и подменённых символов
   - has_tables / has_images_with_text: DOCX-таблицы и текст картинкой —
     классические убийцы парсинга
   - overall: ok | degraded | unreadable + список конкретных проблем
     человеческим языком

2. Ключевое сравнение — расхождение между двумя прочтениями:
   структура от LLM (правильная) против структуры, восстановимой из
   текстового слоя (реальная). Считаем, сколько мест работы, дат и
   скиллов теряется при машинном чтении. Это и есть цифра, которую видит
   пользователь: «ATS увидит 2 места работы из 4».

3. Рекомендации — конкретные, не «улучшите резюме»:
   «одна колонка вместо двух», «почта текстом, а не иконкой»,
   «даты в формате MM.YYYY», «убрать текст из картинки», «не прятать
   опыт в таблицу».

4. API: GET /api/v1/profile/{id}/ats-report. Считается при разборе
   резюме, хранится в профиле (миграция: JSONB-колонка ats_report).

5. Фронт (учесть в фазе 7): баннер на экране профиля, если
   overall != ok. Это первое, что человек должен увидеть после загрузки
   резюме — до всяких вакансий.

6. Тесты: двухколоночная фикстура → unreadable с указанием
   интерливинга; одноколоночная → ok; DOCX с таблицей → degraded;
   отсутствие расхождения между прочтениями на чистой фикстуре.

DoD из CLAUDE.md. Покажи отчёт по обеим PDF-фикстурам.
```

## 2. Drafter-reviewer для сопроводительных → дельта к фазе 6

У них черновик пишет один агент, критикует второй с чистым контекстом,
первый переписывает. Ловит generic-формулировки и упущенные ключевые
слова, которые один проход оставляет.

Добавить в промт фазы 6, к пункту про `/cover-letter`:

```
Генерация сопроводительного идёт в два прохода:
1. Драфтер: профиль + вакансия + application_angle из матча → черновик
2. Ревьюер (отдельный вызов, ЧИСТЫЙ контекст, промт
   app/llm/prompts/review_cover_letter.md): получает вакансию и черновик,
   но НЕ получает рассуждения драфтера. Возвращает структурированную
   критику: упущенные требования вакансии, общие фразы без содержания,
   утверждения, не подтверждённые профилем, оценка тона
3. Драфтер переписывает по критике

Ревьюер обязан проверить главное: нет ли в письме опыта, которого нет в
профиле. Выдуманный опыт — блокирующее замечание, письмо не отдаётся
пользователю с ним.

Оба прохода идут через CLI-провайдера (task=COVER_LETTER), то есть по
подписке. В ответе API возвращается финальное письмо и, отдельным полем,
что исправил ревьюер — пользователь должен видеть, что проверка была.
```

## 3. Свободные deal-breakers → дельта к фазе 5

У них ограничения кандидата — произвольные строки в профиле, и рубрика
оценивает по ним. У нас фильтры зашиты в код.

Добавить в промт фазы 5:

```
CandidateProfile получает поле deal_breakers: list[str] и
preferences: list[str] — произвольный текст, вводится пользователем на
экране профиля («без он-колла», «не букмекеры и не гемблинг», «только
продуктовые компании», «не переезд в другой город»).

Обработка:
- в rule-скоринге НЕ участвуют (текст произвольный, регексом не возьмёшь)
- уходят в промт LLM re-rank отдельным блоком с инструкцией: проверить
  каждый пункт по тексту вакансии, вернуть violated_deal_breakers[] и
  matched_preferences[]
- любой violated_deal_breaker → bucket понижается до skip независимо от
  скора, причина показывается в карточке
- preferences влияют на вердикт, но не на скор

Deal-breakers идут в кэшируемый префикс промта вместе с профилем — они
одинаковы для всех 30 вакансий прогона.
```

## 4. Языковой гейт в два уровня → правка `docs/MATCHING.md`

Сейчас у нас язык — плоский soft-fail −25. Их логика точнее:

| Ситуация | Действие |
| --- | --- |
| Вакансия требует язык, который кандидат **вообще не заявил** | hard-fail |
| Требует уровень **выше** заявленного кандидатом | soft-fail, флаг в карточке, решает человек |
| Требует уровень ≤ заявленного | без штрафа |

Разница принципиальна: немецкий C1 при отсутствии немецкого в профиле —
это не «минус 25 баллов», это стена. А требование C1 при твоём B2 — повод
показать вакансию с пометкой, а не выбросить: граница «свободный
английский» у всех своя.

Обновить таблицу «Этап 0» в `docs/MATCHING.md` до старта фазы 5.

## 5. Калибровка весов по реальным исходам → дельта к фазе 10

В фазе 10 мы планировали тюнить веса на размеченном вручную наборе.
Размеченный набор — это имитация правды. Настоящая правда появится через
два месяца: какие отклики дали приглашение.

Добавить в промт фазы 10:

```
Второй источник разметки, помимо ручного набора: реальные исходы из
таблицы application.

- считаем, при каком скоре отклики реально доходили до интервью
- строим распределение: скор → доля дошедших до скрининга / интервью
- если в бакете apply_now доля приглашений не выше, чем в strong, скоринг
  не работает и порог надо двигать
- скрипт scripts/calibrate_from_outcomes.py: сравнивает предсказанный
  бакет с фактическим исходом, печатает confusion matrix и предлагает
  сдвиг порогов

Минимум 25 разрешённых откликов для осмысленной статистики — при меньшем
числе скрипт отказывается считать и говорит, сколько ещё нужно.
Веса не меняются автоматически, только отчёт.
```

## 6. Генератор коннекторов → дельта к фазе 8

У них `/add-portal` исследует job-борд, проверяет robots.txt, генерирует
скилл по общему контракту и делает тестовый запрос перед регистрацией.
У нас в фазе 8 двадцать пять источников — генератор окупается.

```
scripts/new_source.py + промт app/llm/prompts/scaffold_source.md:
на вход URL job-борда → проверка robots.txt и ToS → определение формата
(есть ли JSON API, какой паттерн URL поиска, структура выдачи) → генерация
файла коннектора по BaseSource, фикстуры и теста → живой тестовый запрос →
отчёт, что получилось.

Ничего не регистрирует автоматически: печатает файлы для ревью. Борд с
запретом в robots.txt или с авторизацией — отказ с объяснением, а не
обход.
```

## Что осознанно не берём

| Что | Почему |
| --- | --- |
| LaTeX-пайплайн для CV с компиляцией и визуальной проверкой PDF | Тянет TeX Live, lualatex, xelatex. На hh отклик идёт профилем, а не PDF. Возможно, отдельным опциональным модулем позже — но не в основной ветке |
| Их `linkedin-search` через `jobs-guest` | Авторы сами пишут, что автодоступ против ToS. Решение по LinkedIn у нас принято и не меняется: `jsearch` + ATS-борды + ручной импорт |
| Файловая архитектура без БД | У нас пайплайн на десятки тысяч вакансий с дедупом и векторным поиском. Файлы этого не выдержат |
| Notion-sync | Дашборд закрывает ту же потребность |
| Gmail-sync (детект статуса отклика по письмам) | Идея хорошая — hh шлёт письма о приглашениях и отказах. Но это отдельный коннектор с OAuth. Кандидат в фазу 12, не сейчас |
| Подготовка к интервью из архива отклика | Логичное продолжение трекера откликов. Фаза 12 |
