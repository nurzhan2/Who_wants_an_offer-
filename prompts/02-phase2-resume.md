# Фаза 2 (ревизия). Резюме → профиль

Заменяет промт фазы 2 из `prompts/02-ingest.md`. Переработан по факту фазы 1.

---

## Решение, принятое до промта: PDF идёт в LLM напрямую

Классический пайплайн «pdfplumber → текст → LLM» ломается на резюме, потому
что резюме почти всегда свёрстано в две колонки (Canva, Enhancv, любой
современный шаблон). `pdfplumber` читает страницу построчно и склеивает
колонки поперёк: «Python Опыт работы Docker Senior Backend PostgreSQL 2021».
LLM потом честно извлекает из этой каши мусор, а ты неделю не понимаешь,
почему матчинг врёт.

Anthropic API принимает PDF нативно, `document`-блоком в base64, и видит
вёрстку. Поэтому:

- **PDF → в LLM как `document`-блок**, без промежуточного текста
- `pdfplumber` остаётся, но только для `raw_text` (полнотекстовый поиск,
  отладка) и как фолбэк, если файл не PDF
- DOCX → текст → LLM (там колонок практически не бывает)

## Решение по модели эмбеддингов

`BAAI/bge-m3`, 1024 dim — оставляем, размерность уже зашита в миграцию и
проверяется при старте. Что нужно знать: это ~2.3 ГБ, первый запуск качает
модель, инференс на CPU i5 — сотни миллисекунд на документ. Отсюда
требования: ленивая загрузка, батчинг, кэш по хешу текста, инференс в
threadpool. Без кэша полный прогон в фазе 8 будет пересчитывать эмбеддинги
тысяч неизменившихся вакансий.

## Промт

```
Фаза 2. Прочитай CLAUDE.md, docs/ARCHITECTURE.md (раздел resume/),
docs/MATCHING.md. Слой данных из фазы 1 готов: модели, репозитории,
миграции, seed.

ЗАДАЧА: загруженное резюме → CandidateProfile + ProfileSkill + эмбеддинг.

ЧЕТЫРЕ МЕСТА, ГДЕ ЭТО ЛОМАЕТСЯ — прочитай до плана:

  (а) Двухколоночные PDF. pdfplumber склеивает колонки поперёк строк, и
      LLM получает бессмыслицу. Поэтому PDF отправляется в Anthropic API
      НАПРЯМУЮ, document-блоком (base64, media_type application/pdf) —
      модель видит вёрстку. Извлечённый pdfplumber текст сохраняется в
      raw_text для полнотекстового поиска и отладки, но в LLM не идёт.
      DOCX и TXT — текстом, там колонок нет.

  (б) total_years нельзя брать у LLM. Человек работает параллельно
      (основная + фриланс + пет-проекты), и сумма длительностей даст
      12 лет опыта у третьекурсника. Считай детерминированно: LLM
      извлекает периоды работы с датами, код сливает пересекающиеся
      интервалы и суммирует объединение. То же для years по каждому
      скиллу. Значение, названное LLM, игнорируется — если оно
      расходится с посчитанным более чем на год, пиши warning в лог.

  (в) Эмбеддинги дорогие. bge-m3 это ~2.3 ГБ и сотни мс на документ на
      CPU. Требования: ленивая загрузка модели (синглтон, грузится при
      первом обращении, не при импорте), инференс через
      asyncio.to_thread — иначе блокируется event loop и сервер
      перестаёт отвечать, батчинг, дисковый кэш по sha256 текста.
      Кэш обязателен: в фазе 8 без него будут пересчитываться тысячи
      неизменившихся вакансий.

  (г) Резюме — это персональные данные. Телефон, почта, адрес, ФИО.
      Ни при каких условиях не логировать текст резюме и его фрагменты.
      В логах только profile_id, размер файла, формат, длительность,
      статус. В отладочный дамп LLM-ответа (если делаешь) — тоже нет.

ЧТО ДЕЛАТЬ:

1. app/resume/extractor.py
   - валидация ДО чтения: размер ≤ 10 МБ, MIME из белого списка
     (pdf, docx, txt, md), проверка сигнатуры файла, а не расширения
   - PDF: pdfplumber → raw_text; если текста < 200 символов, помечаем
     скан (needs_ocr=True) — но для PDF это не критично, в LLM всё равно
     уходит оригинал
   - DOCX: python-docx, включая текст из таблиц (в резюме половина
     содержимого часто в невидимой таблице)
   - возвращает ExtractedDocument(raw_text, page_count, source_format,
     needs_ocr, warnings, file_bytes)
   - OCR не реализуем: для PDF его заменяет нативная отправка в LLM,
     для сканов в DOCX это редкий край. Оставь точку расширения и
     внятную ошибку.

2. app/llm/client.py — обёртка над Anthropic SDK:
   - две модели из settings: ANTHROPIC_MODEL (горячий путь) и
     ANTHROPIC_MODEL_HEAVY (резюме, сопроводительные). Метод принимает,
     какую использовать; дефолт — горячая
   - complete_json(prompt_name, variables, response_model, documents=None)
     → рендер промта из app/llm/prompts/*.md, вызов, валидация ответа
     Pydantic-моделью; при ValidationError один ретрай с текстом ошибки
     в сообщении, при втором провале — LLMError
   - documents: список PDF/изображений, кодируются в base64
     document/image блоки
   - подсчёт input/output токенов и стоимости, в лог структурировано;
     стоимость по прайсу из конфига, а не хардкодом
   - таймаут, tenacity-ретраи на 429/5xx с уважением retry-after
   - никаких промтов инлайном в коде

3. app/llm/prompts/extract_profile.md
   Строгий JSON без преамбулы и без markdown-ограждения. Извлекает:
   ФИО, headline, места работы (компания, должность, дата начала, дата
   окончания или признак «по настоящее время», стек, домен), скиллы с
   уровнем и с указанием, где упомянуты (блок навыков / описание работы /
   проект), языки с уровнем по CEFR, город и страну, готовность к
   релокации, предпочтение по формату работы, зарплатные ожидания с
   валютой, образование.

   Явные требования в промте:
   - резюме может быть на русском, английском, казахском или смешанным —
     язык определяется сам, схема ответа всегда одна
   - даты нормализуются в YYYY-MM; «н.в.», «present», «по настоящее
     время» → null в дате окончания и is_current: true
   - ничего не додумывать: чего нет — null, пустой список
   - НЕ считать суммарный опыт, это делает код
   - не выводить скилл из названия должности, если он нигде не упомянут

4. app/resume/dates.py — детерминированный расчёт (грабля «б»):
   парсинг периодов, слияние пересекающихся интервалов, суммирование
   объединения, отдельно — расчёт лет по каждому скиллу как объединение
   интервалов тех работ, где скилл заявлен. Чистые функции, без БД.

5. app/resume/enricher.py
   - канонизация скиллов по нормализованному словарю. ВАЖНО: полный
     skills.yaml делается в фазе 4. Сейчас — минимальный словарь на
     ~80 самых частых позиций и интерфейс SkillCanonicalizer, чтобы в
     фазе 4 подменить реализацию, не трогая этот модуль
   - уровень владения: из явного указания в резюме, иначе эвристика по
     годам и по тому, где скилл упомянут
   - last_used_year и флаг stale (> 3 лет)
   - вывод seniority из посчитанных лет + заявленных должностей

6. app/resume/profile_builder.py — оркестрация:
   extractor → llm (PDF документом или текстом) → ProfileExtraction →
   dates → enricher → сохранение через ProfileRepository (replace_skills
   из фазы 1) → эмбеддинг. Всё в одной транзакции; при падении на любом
   шаге parse_status = failed с сохранённой причиной.

7. app/matching/embeddings.py
   - интерфейс EmbeddingProvider, реализация BGEM3Provider
   - ленивый синглтон, asyncio.to_thread, батчинг
   - дисковый кэш: sha256(текста + имя модели) → вектор, каталог из
     настроек
   - encode_profile: текст собирается из headline + канонические скиллы +
     должности + домены, НЕ сырое резюме целиком (иначе вектор будет про
     оформление, а не про компетенции)
   - encode_texts(list) — батчевый метод, используется в фазе 3+
   - размерность результата сверяется с settings.EMBEDDING_DIM, иначе
     ошибка

8. API:
   - POST /api/v1/resume/upload (multipart) → 202, {profile_id,
     parse_status}. Разбор в BackgroundTasks
   - parse_status: pending → ready | failed, с полем parse_error и
     parse_started_at. Если pending висит дольше таймаута из конфига —
     считаем failed (процесс мог перезапуститься, BackgroundTasks это
     не переживает); проверка при чтении статуса
   - GET /api/v1/profile/{id} — профиль, скиллы, статус
   - PATCH /api/v1/profile/{id} — ручная правка: добавить/удалить скилл,
     поправить уровень, локацию, релокацию, формат, ожидания. Это
     важный эндпоинт: LLM ошибается, человек должен чинить
   - повторная загрузка резюме создаёт НОВЫЙ профиль, старый помечается
     is_active=False. Историю не теряем

9. Тесты (с маркерами unit / db / slow — заведи их сейчас, к фазе 8
   полный прогон должен уметь идти без БД и без модели):
   - фикстуры настоящих резюме в tests/fixtures/resumes/: одноколоночный
     PDF, ДВУХколоночный PDF, DOCX с таблицей, TXT, PDF на английском,
     PDF со смешанным ru/en
   - dates.py параметризованно: параллельные работы не удваивают опыт;
     разрыв в стаже не схлопывается; «по настоящее время» считается до
     сегодня; работа на один месяц; перевёрнутые даты не ломают
   - LLM замокан; невалидный JSON → ретрай; второй невалидный → LLMError
     и parse_status=failed
   - эмбеддинги: провайдер подменяется фейком, реальная модель в CI не
     грузится; кэш попадает со второго вызова; несовпадение размерности
     даёт ошибку
   - отказ на файле 20 МБ, на .exe с расширением .pdf (проверка
     сигнатуры), на пустом файле
   - в логах нет текста резюме: тест перехватывает лог и ищет строку из
     фикстуры

ЧЕГО НЕ ДЕЛАТЬ:
   - не отправлять извлечённый pdfplumber-текст в LLM для PDF
   - не доверять LLM подсчёт лет
   - не грузить модель эмбеддингов при импорте модуля
   - не делать полный skills.yaml — это фаза 4
   - не логировать содержимое резюме

DoD из CLAUDE.md. Прогони ruff, mypy, pytest, покажи вывод, отдельно —
результат разбора двухколоночного PDF-резюме (структура профиля, без
персональных данных в выводе).

Сначала план, потом код.
```

## На что смотреть в ревью

1. Двухколоночное резюме разобралось корректно — это главный тест фазы.
   Проверь глазами: скиллы не перемешались с должностями.
2. `total_years` считается кодом, не берётся из ответа LLM. Поищи в
   `profile_builder.py`, не присваивается ли поле напрямую из
   `extraction.total_years`.
3. Модель эмбеддингов не грузится при `import` — иначе тесты и старт
   сервера будут ждать 2.3 ГБ.
4. `asyncio.to_thread` вокруг инференса есть. Без него первый же запрос
   заблокирует весь сервер на секунду.
5. В тестах есть маркеры, и `pytest -m "not db and not slow"` проходит
   без базы и без модели.
