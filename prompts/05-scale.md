```
- adzuna: GET https://api.adzuna.com/v1/api/jobs/{country}/search/{page},

{ats: greenhouse, token: acme, name: Acme, tags: [fintech, eu]}.
Наполни стартовый список 60+ компаниями: казахстанский теx-сектор,

БАТЧ 4 (HTML/внутренний JSON):

  selectolax или lxml, не BeautifulSoup

- djinni: HTML
- enbek: KZ, государственный портал
Перед реализацией каждого — проверь robots.txt и зафиксируй в докстринге
класса, что именно разрешено. Если запрещено — не реализуй, напиши мне.

  app/llm/prompts/parse_telegram_post.md), посты не про вакансии

- дедуп с остальными источниками через общий fingerprint
- обработка отсутствия сессии: источник просто не активен, не падает

ТРЕБОВАНИЯ:

- LinkedIn, Indeed, Glassdoor — не реализовывать
- Каждый источник: тест на нормализацию + отметка в docs/SOURCES.md о

- Итоговый отчёт: таблица «источник → сколько вакансий отдал на тестовом
  профиле»

DoD из CLAUDE.md. Сначала план, потом код. Реализуй батчами, после
каждого батча — коммит и пауза на моё ревью.
```

## Промт фазы 9 — планировщик и уведомления

```
Фаза 9. Прочитай CLAUDE.md.

ЗАДАЧА: система должна работать сама, без ручных запусков.

1. app/pipeline/scheduler.py на APScheduler (AsyncIOScheduler):
   - полный прогон по всем источникам раз в N часов (конфиг)
   - инкрементальный прогон (только опубликованное за последние 24ч)
     чаще, каждые M часов
   - джоба переоценки: rescore при изменении профиля или весов
   - джоба обслуживания: пометка протухших вакансий is_active=False,
     чистка сырых raw-данных старше 90 дней, VACUUM
   - персистентный jobstore в БД, защита от параллельного запуска одной
     джобы (advisory lock в Postgres)
   - graceful shutdown

2. app/notifications/telegram.py:
   - бот шлёт уведомление о вакансиях со score >= порога из конфига
   - формат: заголовок, компания, вилка, скор, 2–3 недостающих скилла,
     вердикт одной строкой, кнопки «Открыть», «В отклики», «Скрыть»
   - дневной дайджест утром: сколько новых, топ-5, что изменилось
   - антиспам: одна вакансия уведомляется один раз, батчинг при
     большом количестве, тихие часы из конфига
   - отсутствие TELEGRAM_BOT_TOKEN не ломает пайплайн

3. Трекер откликов: автоматический перевод в статус stale, если отклик
   висит в applied больше 14 дней; напоминание в Telegram.

4. Наблюдаемость: эндпоинт /metrics в формате Prometheus
   (количество вакансий, длительность прогонов, ошибки по источникам,
   потраченные LLM-токены и стоимость), структурированные логи с
   run_id сквозным.

5. Тесты: планировщик регистрирует ожидаемые джобы; advisory lock
   не даёт двойной запуск; уведомление не дублируется; тихие часы
   соблюдаются.

DoD из CLAUDE.md. Сначала план, потом код.
```

```
Фаза 10. Прочитай CLAUDE.md и docs/MATCHING.md.

ЗАДАЧА: не новые фичи, а точность. Сейчас система работает — надо, чтобы
она не врала.

1. Создай размеченный набор: scripts/build_eval_set.py выгружает 100
   вакансий из БД, я размечаю их вручную в CSV (бакет + причина).
   Формат и инструкция — в docs/EVAL.md.

5. По результатам — конкретные правки: расширение skills.yaml,

6. Отчёт в docs/EVAL.md: текущие метрики, что чинили, что осталось.
```

## Промт фазы 11 — деплой

```
Фаза 11. Прочитай CLAUDE.md.

ЗАДАЧА: воспроизводимый прод-деплой на одном VPS.

1. Прод docker-compose.prod.yml: db (pgvector, volume, healthcheck),
   api (gunicorn + uvicorn workers, non-root, ресурсные лимиты),
   worker (планировщик отдельным процессом), caddy (reverse proxy,
   автоматический Let's Encrypt), frontend (статика, собранная
   в build-стадии, отдаётся caddy).

2. Многостадийные Dockerfile: backend на python:3.12-slim с uv,
   отдельная стадия для скачивания модели эмбеддингов в образ
   (иначе первый запрос будет ждать 2 ГБ); frontend node:20 → nginx/caddy.

3. Миграции применяются отдельной one-off командой при деплое,
   не в entrypoint api.

4. scripts/backup.sh — pg_dump по расписанию, ротация 7 дней,
   опциональная выгрузка в S3-совместимое хранилище. И
   scripts/restore.sh с проверкой.

5. .github/workflows/deploy.yml — по тегу: сборка образов, пуш в GHCR,
   деплой по SSH, применение миграций, health-check, откат при провале.

6. docs/DEPLOY.md: пошагово от чистого VPS до работающего сервиса,
   список переменных окружения, что делать при типовых сбоях
   (кончился диск, упал коннектор, исчерпан лимит Adzuna, протухла
   Telegram-сессия).

7. Безопасность: БД не торчит наружу, дашборд закрыт basic-auth или
   Cloudflare Access, секреты только через env-файл с правами 600,
   .env в .gitignore проверен, в образах нет ключей.

8. Проверь весь путь целиком на чистой машине или в локальном
   docker-окружении и покажи вывод.

DoD из CLAUDE.md. Сначала план, потом код.
```
