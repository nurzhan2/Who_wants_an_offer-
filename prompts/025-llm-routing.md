# Дельта к фазе 2 → фаза 2.5. Маршрутизация LLM

Короткая фаза между 2 и 3. `llm/client.py` не выбрасывается — он
становится одной из трёх реализаций за общим протоколом.

## Зачем

Задачи в системе принципиально разные по объёму и по требованиям:

| Задача | Частота | Латентность важна | Провайдер |
| --- | --- | --- | --- |
| Разбор резюме | ~1 раз | нет | **Claude Code CLI** (подписка) |
| Сопроводительное письмо | по клику | терпимо | **Claude Code CLI** |
| Генерация `skills.yaml`, фикстур, eval-набора | разово, при разработке | нет | **Claude Code CLI** |
| Разбор Telegram-поста | сотни/сутки | нет, ночной батч | **Ollama** локально |
| Разбор вставленной вакансии | по клику | да | **API**, горячая модель |
| Re-rank топ-30 | ~120/сутки | да | **API** + кэш промта |

Гонять re-rank и парсинг Telegram через CLI нельзя: спавн процесса на
каждый вызов, никакого батчинга, посессионные лимиты подписки, отсутствие
structured outputs. Гонять разбор резюме через API — платить за то, что
уже покрыто подпиской.

## Промт

```
Фаза 2.5. Прочитай CLAUDE.md и app/llm/client.py из фазы 2.

ЗАДАЧА: вынести LLM за протокол и добавить маршрутизацию по типу задачи.
Существующий Anthropic-клиент сохраняется целиком, меняется только его
место в иерархии.

1. app/llm/base.py
   - LLMTask(StrEnum): RESUME_EXTRACTION, TELEGRAM_PARSE, VACANCY_PARSE,
     RERANK, COVER_LETTER, TOOLING
   - LLMUsage: provider, model, input_tokens, output_tokens,
     cache_read_tokens, cost_usd, duration_ms,
     accounting: Literal["measured", "estimated", "subscription"]
   - LLMProvider(Protocol):
       async def complete_json(prompt_name, variables, response_model,
           task, documents=None, effort=None, cached_prefix=None)
           -> tuple[BaseModel, LLMUsage]
       def is_available(self) -> bool
   - LLMRouter: по LLMTask выбирает провайдера из конфига; при
     недоступности — фолбэк по цепочке из конфига с обязательным WARNING
     в лог (какая задача, кто был выбран, кто реально отработал).
     Молчаливого фолбэка быть не должно.

2. app/llm/providers/anthropic_api.py — существующий client.py целиком,
   переименован и приведён к протоколу. Логику не переписывать.

3. app/llm/providers/claude_cli.py — новый.
   - вызов через asyncio.create_subprocess_exec("claude", "-p", prompt,
     "--output-format", "json", "--max-turns", "1").
     НИКОГДА через shell: промт содержит текст резюме и постов из
     Telegram, то есть недоверенный ввод, shell=True это инъекция
   - инструменты отключены: --allowedTools ""
   - для PDF: --allowedTools "Read" плюс абсолютный путь к файлу в
     промте, рабочий каталог ограничен каталогом файла. Claude Code
     читает PDF нативно, вёрстка сохраняется — эквивалент document-блока
     в API
   - structured outputs НЕТ: промт требует чистый JSON, ответ проходит
     снятие markdown-ограждения и Pydantic-валидацию; ретраев два, а не
     один, вероятность мусора выше
   - CLI отдаёт JSON с полями стоимости и длительности — парсим в
     LLMUsage с accounting="subscription"
   - таймаут из конфига, при превышении kill процесса и внятная ошибка
   - семафор на 2 параллельных вызова: это локальный CLI, не сервер
   - is_available(): наличие бинаря `claude` в PATH, проверяется один
     раз и кэшируется
   - если ENVIRONMENT=production и cli выбран в маршрутизации — падать
     на старте с объяснением. Подписочная авторизация не предназначена
     для серверного прода

4. app/llm/providers/ollama.py — новый.
   - httpx к OLLAMA_BASE_URL, /api/chat с format="json"
   - модель из конфига (OLLAMA_MODEL)
   - основной путь для TELEGRAM_PARSE: задача простая, объём большой
   - accounting="measured", cost_usd=0
   - is_available(): пинг /api/tags
   - фолбэк на API при недоступности, с WARNING

5. Маршрутизация в settings, меняется без правки кода:
     LLM_ROUTING={"resume_extraction":"cli","cover_letter":"cli",
                  "telegram_parse":"ollama","vacancy_parse":"api",
                  "rerank":"api","tooling":"cli"}
     LLM_FALLBACK_CHAIN={"cli":["api"],"ollama":["api"],"api":[]}
   Валидатор: все задачи покрыты, все провайдеры известны, цепочки не
   зациклены.

6. ДВА РЫЧАГА ПО СТОИМОСТИ — реализовать сразу, они дают больше, чем сам
   выбор провайдера:

   а) Кэширование промта в API-провайдере. В re-rank профиль кандидата
      одинаков во всех 30 вызовах. Без кэша он оплачивается 30 раз по
      $2/MTok, с кэшем — один раз полностью и 29 раз по $0.50/MTok.
      Профиль ставится ПЕРВЫМ блоком сообщения с cache_control
      ephemeral, вакансия после него. Порядок принципиален: кэшируется
      префикс. Отсюда аргумент cached_prefix в протоколе.

   б) Двухступенчатый re-rank (задел, включается в фазе 5): дешёвая
      модель проходит все 30, дорогая — только топ-10. Модели ступеней
      в конфиге.

7. app/llm/usage.py — единый учёт: каждый вызов пишет LLMUsage
   структурированно и агрегируется в счётчик прогона; /metrics отдаёт
   суммы по провайдерам и задачам. accounting отличает измеренное от
   оценённого и от подписки — в одну сумму не складывать.

8. scripts/parse_resume.py — правка: работает через роутер, то есть БЕЗ
   ANTHROPIC_API_KEY, через CLI. Этот скрипт закрывает долг фазы 2.

9. Тесты:
   - роутер выбирает провайдера по задаче; фолбэк срабатывает и пишет
     WARNING (тест проверяет запись в логе, а не только результат)
   - CLI: subprocess замокан, разбор JSON-вывода, таймаут убивает
     процесс, ответ в markdown-ограждении распаковывается, невалидный
     JSON → два ретрая → ошибка
   - CLI не вызывается через shell: тест проверяет использование
     create_subprocess_exec со списком аргументов
   - ENVIRONMENT=production + cli в маршрутизации → падение на старте
   - Ollama замокан, при недоступности фолбэк на API
   - cache_control стоит на первом блоке, а не на последнем
   - ни одного реального вызова к CLI, Ollama или API в CI

ЧЕГО НЕ ДЕЛАТЬ:
   - не переписывать существующий Anthropic-клиент, только переместить
   - не гонять rerank и telegram_parse через CLI
   - не использовать shell=True ни при каких условиях
   - не смешивать subscription и measured в одной сумме стоимости

DoD из CLAUDE.md. После — прогони scripts/parse_resume.py через CLI на
двухколоночной фикстуре и покажи долг фазы 2: структуру профиля,
посчитанный total_years против заявленного моделью, блок стоимости.

Сначала план, потом код.
```

## Плюс правка из ревью фазы 2

В `enricher.py` разделить две разные сущности:

- `level` — насколько владеет. При отсутствии доказательств по датам →
  `working` (нейтральный множитель), **не** `basic`
- `evidence` — `corroborated` (подтверждён датами работ) / `stated`
  (только заявлен в сайдбаре)

Сейчас скилл, упомянутый только в блоке навыков, получает `basic` и режет
скор на 30%. Но стек по работам выписывают не все, и системный штраф за
оформление резюме — это ошибка измерения, а не свойство кандидата.
`evidence` уходит в UI и в контекст LLM-вердикта; решение, штрафовать ли
`stated`, принимается в фазе 5 на размеченном наборе, а не по умолчанию.

Требуется миграция `0003` (новая колонка `evidence` в `profile_skill`) —
делать вместе с этой дельтой, пока фаза 3 не началась.

## На что смотреть в ревью

1. `shell=True` отсутствует нигде.
2. `cache_control` на **первом** блоке. На последнем он бесполезен.
3. Фолбэк пишет WARNING — иначе разное качество извлечения без следа.
4. `accounting` разделяет подписку и деньги, иначе `/metrics` врёт.
